# Engineering Policy

## Назначение

Этот skill используется для получения и применения актуальных внутренних инженерных правил ДВГУПС.

Канонический источник общих инженерных правил:

```text
https://repo.dvgups.ru/docs/
```

Содержимое Wiki не должно дублироваться в этом skill или в `AGENTS.md` конкретного репозитория.

Skill предоставляет текущему workflow применимые организационные ограничения и не подменяет специализированный workflow, который выполняет саму задачу.

## Когда использовать

Применяй skill, если задача затрагивает хотя бы одну из областей:

- Git workflow;
- выбор или именование ветки;
- commits и pull requests;
- release или hotfix;
- общие правила разработки;
- тестирование;
- review тестов;
- accessibility;
- web quality;
- security;
- REST/API conventions;
- внутренние стандарты разработки;
- другие организационные правила, на которые ссылается репозиторий.

Не используй skill только потому, что Wiki доступна.

Если задача полностью определяется локальными правилами репозитория и не требует организационной политики, дополнительное чтение Wiki не нужно.

## Источники и приоритет

Нормативные источники применяются в следующем порядке:

```text
явные требования текущей задачи
        ↓
ближайшие repo-specific AGENTS.md / RULES.md
        ↓
внутренняя Wiki ДВГУПС
```

Repo-specific правила могут специализировать общие правила Wiki.

Не считай локальное правило отменой общей политики, если это явно не указано.

Фактическое состояние репозитория используется как источник сведений о:

- текущей реализации;
- конфигурации;
- структуре проекта;
- доступных командах;
- используемых зависимостях;
- существующих инструментах.

Фактическое состояние репозитория само по себе не отменяет и не переопределяет нормативные правила.

Существующее нарушение правила является текущим состоянием или техническим долгом, а не основанием автоматически повторять такое поведение.

Если применимые нормативные источники существенно противоречат друг другу:

1. не выбирай правило молча;
2. зафиксируй конфликт;
3. определи, влияет ли конфликт на текущую задачу;
4. если без решения продолжать небезопасно или невозможно — передай решение человеку.

## Доступ к Wiki

Используй только настроенные read-only Wiki tools.

Предпочтительный workflow:

```text
1. wiki_status
2. определить необходимую область политики
3. wiki_list_pages при необходимости discovery
4. wiki_get_page только для релевантных документов
5. выделить правила, применимые к текущей задаче
```

Не загружай все страницы Wiki.

Не вызывай `wiki_list_pages`, если точный документ уже известен.

Не открывай документы, которые не относятся к текущей задаче, только ради дополнительного контекста.

## Авторизация

Skill не управляет авторизацией.

Запрещено:

- запрашивать login/password пользователя;
- искать credentials;
- читать browser profile;
- читать cookies;
- читать OAuth tokens;
- пытаться самостоятельно выполнить Gitea login;
- обходить отсутствие авторизации другими способами.

Если Wiki tool сообщает отсутствие авторизации:

```text
WIKI_AUTH_REQUIRED
```

останови действия, зависящие от Wiki, и сообщи, что требуется ручное восстановление Wiki-сессии.

Если Wiki недоступна по технической причине, не подменяй внутреннюю политику знаниями модели.

Не считай ранее запомненное содержание Wiki актуальной версией правил.

## Выбор документа

Загружай только документы, относящиеся к текущей задаче.

Примеры маршрутизации:

```text
ветки / commits / PR / hotfix / release
→ Git Agent Rules / Git Workflow

добавление, изменение или review тестов
→ Test Rules

общие инженерные решения / scope / public contracts
→ Code Rules

UI / accessibility / keyboard / focus / HTML / web security
→ Web Quality Rules

REST / HTTP / DTO / OpenAPI
→ REST API Rules
```

Это примеры, а не жёстко зашитый список.

Используй актуальную структуру Wiki, полученную через Wiki tools.

Если один документ ссылается на дополнительный профиль, открывай его только тогда, когда этот профиль действительно относится к текущей задаче.

## Работа с полученными правилами

После чтения документа:

1. выдели только правила, применимые к текущей задаче;
2. не пересказывай весь документ;
3. не копируй правила в repository без отдельной необходимости;
4. применяй правила как ограничения текущего workflow;
5. сохраняй терминологию и смысл канонического источника;
6. не придумывай отсутствующие внутренние правила;
7. не расширяй область применения правила по аналогии без подтверждения;
8. не сохраняй нерелевантную часть документа в дальнейшем контексте.

Если правило не относится к задаче, не добавляй его в контекст дальнейшей работы.

## Repo-specific правила

Wiki задаёт organization-level правила.

Конкретный repository отвечает за собственные:

- архитектурные инварианты;
- публичный API;
- package contract;
- команды;
- структуру;
- локальные quality gates;
- особенности release;
- ограничения конкретного продукта;
- поддерживаемые инструменты;
- конкретный способ проверки результата.

Не используй общие правила Wiki для навязывания архитектуры, не применимой к текущему repository.

Например, application-specific требования к SvelteKit, FSD, DDD или server architecture не должны автоматически применяться к UI-библиотеке только потому, что присутствуют в общей инженерной документации.

## Интеграция с текущим workflow

Получение политики не является самостоятельным процессом разработки.

Обычная последовательность:

```text
текущая задача / workflow
        ↓
определить применимые policy domains
        ↓
получить только нужные Wiki pages
        ↓
сопоставить Wiki с repo-specific rules
        ↓
выделить применимые ограничения
        ↓
передать ограничения текущему workflow
```

После этого специализированный workflow продолжает выполнение задачи.

Например:

```text
engineering-policy
        ↓
policy constraints
        ↓
change-contract
```

или:

```text
engineering-policy
        ↓
policy constraints
        ↓
component-audit
```

или:

```text
engineering-policy
        ↓
policy constraints
        ↓
implementation workflow
```

или:

```text
engineering-policy
        ↓
policy constraints
        ↓
change-verification
```

Skill не должен самостоятельно захватывать обязанности других workflows.

## Результат

Результатом skill является минимальный набор организационных правил, применимых к текущей задаче.

При необходимости зафиксируй:

- применённые policy domains;
- канонические Wiki pages;
- существенные ограничения;
- repo-specific специализации;
- обнаруженные конфликты;
- blockers.

Предпочтительный смысл результата:

```text
policy_domains
sources
constraints
repo_specific_overrides
conflicts
blockers
status
```

Не создавай отдельный постоянный артефакт в repository, если он не нужен следующему workflow или явно не требуется задачей.

Не дублируй содержимое Wiki в результате.

Передавай только те ограничения, которые реально нужны следующему этапу.

## Отчёт пользователю

Если внутреннее правило существенно повлияло на решение, кратко укажи:

- какой policy domain применялся;
- какое ограничение или требование повлияло на решение;
- был ли обнаружен конфликт с repo-specific правилами;
- остались ли blockers.

Не выводи длинные выдержки из Wiki без необходимости.

Если пользователь запросил инженерную работу, не заканчивай ответ простым пересказом политики: передай результат следующему применимому workflow.

## Stop conditions

Останови policy-dependent часть workflow, если:

- Wiki требует ручной авторизации;
- Wiki технически недоступна;
- необходимый нормативный источник невозможно получить;
- нормативные источники существенно конфликтуют и решение влияет на безопасность или корректность задачи;
- невозможно определить применимое правило без догадки;
- продолжение потребовало бы обхода ограничений доступа.

Не компенсируй эти состояния предположениями модели.

## Ограничения

Этот skill:

- не изменяет Wiki;
- не управляет Wiki authentication;
- не запрашивает и не читает credentials;
- не создаёт собственную копию базы знаний;
- не заменяет repo-specific `AGENTS.md`;
- не заменяет специализированные workflow skills;
- не выполняет brainstorming;
- не составляет implementation plan;
- не выполняет реализацию вместо специализированного workflow;
- не выполняет финальную verification вместо `change-verification`;
- не должен использоваться для загрузки всей внутренней документации;
- не превращает текущее состояние repository в нормативное правило.
